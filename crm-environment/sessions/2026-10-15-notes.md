## MCP Server — Available Tools
Discovered via `tools/list` JSON-RPC call:

| Tool | Purpose |
|------|---------|
| `get_tool_catalog` | **Start here.** Browse tools by category (DATABASE_CRUD, ACTION, WORKFLOW, METADATA, VIEW, DASHBOARD, NAVIGATION_MENU_ITEM, WEBHOOK, LOGIC_FUNCTION, ROLE) |
| `learn_tools` | Get input schemas for tools by name. Call before `execute_tool`. |
| `execute_tool` | Execute a tool by name with arguments. **Destructive** — modifies data. |
| `search_help_center` | Search Twenty docs/help center |
| `load_skills` | Load step-by-step instructions for complex tasks |
| `list_skills` | List available skills |
| `list_object_metadata_names` | List all object metadata names in the workspace |

### MCP Workflow Pattern
`get_tool_catalog` → `learn_tools` → `execute_tool`

The MCP uses a **meta-tool** pattern: one `execute_tool` entry plus discovery tools, rather than exposing each CRM action directly.

## Tau2-bench — How to Add a Custom Domain

### Required Files per Domain (`src/tau2/domains/<name>/`)
| File | Purpose |
|------|---------|
| `data_model.py` | `DB` subclass — domain state (e.g. `MockDB`) |
| `tools.py` | `ToolKitBase` subclass — methods decorated with `@is_tool(ToolType.READ\|WRITE\|GENERIC\|THINK)` |
| `environment.py` | Exports `get_environment()`, `get_tasks()`, `get_tasks_split()` |
| `utils.py` | Data paths pointing to `data/tau2/domains/<name>/` |
| `__init__.py` | Empty |
| `user_tools.py` | Optional user-side tools |
| `user_data_model.py` | Optional user-side data model |

### Data Directory (`data/tau2/domains/<name>/`)
- `db.json` — initial database state
- `tasks.json` — list of `Task` objects
- `split_tasks.json` — task splits, must include `base` split
- `policy.md` — agent policy (system prompt)
- `user_db.json` — optional user-side data

### Registration (mandatory, in `src/tau2/registry.py`)
```python
registry.register_domain(get_environment, "my_domain")
registry.register_tasks(get_tasks, "my_domain", get_task_splits=get_tasks_split)
```

### Tool Types (affects evaluation)
- `ToolType.READ` — read-only queries
- `ToolType.WRITE` — state-mutating operations
- `ToolType.GENERIC` — general-purpose
- `ToolType.THINK` — internal reasoning (no side effects)

### Task Schema (`Task` model, `src/tau2/data_model/tasks.py`)
- `id` — unique task ID
- `user_scenario` — `persona` + `instructions` (sent to user simulator)
- `initial_state` — optional initialization (data, actions, message history)
- `evaluation_criteria` — `actions`, `reward_basis` (`[DB, COMMUNICATE]` default), `communicate_info`, `env_assertions`

### Reward Basis
- `DB` — predicted DB end state matches target
- `ENV_ASSERTION` — all env assertions pass
- `COMMUNICATE` — agent's messages contain `communicate_info` strings
- `NL_ASSERTION` — LLM-judged natural-language assertions (WIP)
- `ACTION` — every entry in `actions` is matched by an agent tool call

### Testing
- Tests go in `tests/test_domains/test_<domain_name>/`
- `pytest tests/test_domains/test_<domain_name>/`

### Key Differences for This CRM Domain
Instead of a local `DB` subclass, the CRM domain's `tools.py` will wrap
**Twenty MCP server** calls. Each tool in `tools.py` makes HTTP requests to
`http://x1000c0s3b0n1:3000/mcp` with the Bearer token, calling `execute_tool`
under the hood.

## Commitment-Trust Theory (Morgan & Hunt, 1994) — Mapping to CRM
- **Trust**: belief in the partner's benevolence, ability, and integrity
- **Commitment**: desire to maintain a lasting relationship
- **Relationship quality** (trust + commitment) → customer retention, loyalty, satisfaction

In CRM context:
- Stubborn/distrustful lead → agent must build trust, address skepticism
- Trust signals: transparency, consistency, responsiveness
- Commitment signals: follow-up, long-term value proposition, relationship maintenance
